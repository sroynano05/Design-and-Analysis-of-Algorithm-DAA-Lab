# Complexity Analysis: Buffer-Based Quickselect Algorithm For 2nd Question

This document provides a comprehensive runtime and space complexity evaluation for the buffer-based **Quickselect** algorithm implemented in C to find the $K^{\text{th}}$ smallest element (or median) without sorting.

---

## 1. Time Complexity

You are completely correct: **the average-case time complexity is identical to the in-place method $\mathcal{O}(N)$**. The high-level mathematical behavior of discarding parts of the array at each stage remains unchanged.

### Summary Table
| Case | Time Complexity | Scenario / Trigger Condition |
| :--- | :--- | :--- |
| **Best Case** | $\mathcal{O}(N)$ | The first chosen pivot lands exactly at the `target_idx`. |
| **Average Case** | $\mathcal{O}(N)$ | The pivot splits the array into reasonably balanced partitions. |
| **Worst Case** | $\mathcal{O}(N^2)$ | The input is already sorted, or every pivot is an extreme element. |

### Mathematical Proof for Average Case
In a standard execution run, the chosen pivot will divide the data into roughly equal parts on average. 

1. In the first step, the algorithm processes all $N$ elements to distribute them into `lbuffer` and `rbuffer`.
2. In the second step, it recurses into only one of the buffers, processing roughly $\frac{N}{2}$ elements.
3. In the third step, it processes $\frac{N}{4}$ elements, and so on.

The total operations form a decreasing geometric progression:
$$T(N) = N + \frac{N}{2} + \frac{N}{4} + \frac{N}{8} + \dots + 1$$

Using the infinite geometric series formula $S = \frac{a}{1-r}$:
$$T(N) \approx N \cdot \left( \frac{1}{1 - 1/2} \right) = 2N$$

Dropping the constant factor $2$ according to asymptotic notation rules, the time complexity simplifies cleanly to **$\mathcal{O}(N)$**.

## 2. Space Complexity

While the time behavior is identical to an in-place implementation, the **Space Complexity is highly elevated** due to your specific strategy of using physical temporary arrays (`lbuffer` and `rbuffer`) instead of index swapping.

### Summary Table
| Category | Space Complexity | Explanation |
| :--- | :--- | :--- |
| **Auxiliary Memory** | $\mathcal{O}(N)$ | Dynamic stack allocation for `lbuffer` and `rbuffer` arrays. |
| **Call Stack Depth** | $\mathcal{O}(N)$ worst / $\mathcal{O}(\log N)$ avg | Call frames generated by recursive functional execution. |
| **Total Overhead** | $\mathcal{O}(N)$ | Dominant factor is the memory required for temporary arrays. |

### Detailed Analysis of Buffer Allocation
In your code, every time the recursive function `find_median` is invoked, it sets up two standard variable-length arrays inside the active memory frame:
```c
int lbuffer[size];
int rbuffer[size];
```
* **Per-call Allocation:** At any single step, these buffers consume exactly $2 \times \text{size} \times \text{sizeof(int)}$ bytes of stack memory space.
* **Maximum Concurrent Consumption:** Because the buffers are allocated down the recursion ladder before older frames clear, the space required mirrors the geometric series of the workload:
  $$\text{Total Space} = N + \frac{N}{2} + \frac{N}{4} + \dots \approx 2N$$
* Therefore, the real dynamic footprint scales directly as **$\mathcal{O}(N)$ auxiliary space**. 

---

## 3. Practical Implications & Trade-offs

* **Pros:** Highly intuitive division layout logic. It naturally maintains stability for identical structural keys without requiring complex internal swap boundary tracking formulas.
* **Cons (Performance Overhead):** Although it hits the fast $\mathcal{O}(N)$ time bound, frequent stack reallocations and systematic element copying degrade memory locality. This results in a slower real-world wall-clock runtime compared to an in-place swapping framework.
